# Danaan Agent 25 分钟逐页演讲稿

适配文件：`Danaan_Agent_项目分享_时间精简版.pptx`  
总时长：25 分钟

## 第 1 页｜0.5m｜封面

大家好，我今天分享的项目是 Danaan Agent。

它最初从云资源申请这个具体场景出发。我们的目标不是简单把一张申请表搬到聊天窗口，而是帮助用户理解资源属性、补齐申请信息，并在受控的流程中提交请求。

在接下来的 25 分钟里，我会先讲清客户为什么需要这项能力，再介绍项目从第一版 Demo 到 Agent Skill 平台的演进，最后在 Dev 环境现场演示一次 Cloud SQL 资源申请。

## 第 2 页｜0.5m｜分享路线

整场分享可以概括为四个问题。

第一，客户在申请云资源时到底遇到了什么问题。第二，为什么第一版能跑通流程，却还不能满足真实交互需求。第三，我们如何通过 Agent 和 Skill 把业务能力沉淀为可扩展的平台。最后，我会用一个 Cloud SQL 申请演示，展示用户从自然语言请求到受控提交的全过程。

## 第 3 页｜2m｜用户的真实障碍

项目的起点来自一个非常实际的问题。

当客户的业务用户需要申请 Cloud SQL、BigQuery 或 Cloud Storage 等云资源时，通常面对的是一组专业资源属性。用户可能知道自己需要数据库，但不清楚实例规格、区域、数据库版本、存储配置等资源属性分别代表什么，也不知道哪些信息缺失，哪些选择会相互影响。

因此，一张传统的申请表并不能真正解决问题。用户往往要反复咨询云平台团队，再补充信息、修改 Ticket。云平台团队也需要持续处理大量高频、重复的问题。

Danaan Agent 希望把这部分沟通前移到申请过程本身。用户可以先说出业务目标，Agent 再用用户能理解的语言解释某一个云资源属性的具体含义，并根据当前信息继续追问。这样，申请不再只是把资源属性填完，而是一个帮助用户做出正确选择的过程。

## 第 4 页｜2.5m｜第一版 LangGraph Demo

在项目开始阶段，我们先用 LangGraph 做了第一版 Demo，目标很明确：快速验证资源申请闭环能否跑通。

第一版证明了这个方向是可行的。用户可以发起资源申请，系统能够收集必要信息、构造申请内容，并完成提交链路。

但在继续扩展时，我们发现第一版采用的固定流程设计存在明显边界。每增加一种资源、一个参数校验规则，或者一个用户分支，都需要增加控制逻辑。比如，用户在中途修改需求、补充资源属性，或者提出“这个参数是什么意思”，流程需要提前把这些分支写进去。

这种方式适合快速做 Demo，但不适合长期承载多个业务场景。真实用户不会完全按预设顺序回答问题，他们会追问、跳过、修改，甚至把多个需求放在同一句话里。

这就是我们做架构演进的原因：从固定流程，走向能够结合上下文持续判断下一步的 Agent。

## 第 5 页｜2m｜用 Skill 承载业务能力

我们的关键技术决策，是用 Skill 承载业务能力。

平台负责通用能力，包括对话、会话状态、页面交互、任务编排和受控工具调用。Skill 则负责领域规则，例如什么时候处理资源申请、需要收集哪些资源属性、哪些输入需要校验，以及允许调用哪些 Tool。

这样做的价值是，新的业务场景不需要重新搭建一套完整流程。我们可以复用平台已有的会话、工具调用和确认机制，再通过一个新的 Skill 增加相应的业务规则。

这里要强调一点：Skill 不替代程序校验和权限控制。模型负责理解用户表达、决定下一步需要什么信息；确定性的规则、权限和外部系统调用，仍然由受控的程序和 Tool 执行。

## 第 6 页｜3m｜Agent Loop 与平台组件

这一页展示的是 Agent Loop，也是项目从第一版 Demo 演进后的核心。

用户发起请求后，Agent 先理解需求，并读取当前会话中的历史信息。随后，它会根据匹配的 Skill 获取领域规则，例如申请 Cloud SQL 时需要确认哪些资源属性、哪些输入必须由用户明确确认。

接下来，模型判断下一步。如果信息不足，它会向用户澄清；如果信息足够，它会准备调用相应的 Tool。Tool 返回结果后，结果会写回当前上下文，Agent 再进行下一轮判断。

因此，这里不是一条固定的单向流程，而是一个循环：理解请求、判断下一步、调用工具、读取结果，再根据结果继续判断。

对于会产生副作用的操作，例如正式提交资源申请，系统不会直接执行。它会先展示申请摘要，等待用户确认。用户确认后，受控执行层才允许调用 MCP 或自定义 Tool。

底部的 Sandbox 负责会话工作区、文件和产物管理，为生产运行提供隔离边界。这个设计让 Agent 可以保持灵活的交互，同时让真正的外部操作处于可控、可确认的范围内。

## 第 7 页｜3m｜已落地的三个 Skill

平台能力已经通过三个业务 Skill 得到验证。

第一个是 Danaan Cloud Resource。它负责创建云资源申请，目前已经跑通从资源识别、属性解释、参数收集、校验到用户确认和提交的完整闭环。

第二个是 Cost Consultant。它面向已有资源的成本查询和分析，可以基于 GCP、AliCloud 的历史费用，支持应用、GKE Namespace 和云服务等维度的分析。

第三个是 Cost Estimation。它面向新用例，通过合同价、SKU 映射和历史回溯等信息，帮助客户估算新的云资源使用场景可能带来的成本。

这三个 Skill 的意义不只是多了三个功能。它们验证了同一套平台可以承载不同类型的云业务：资源申请属于流程与治理问题，费用查询属于数据分析问题，成本估算属于决策支持问题。

## 第 8 页｜2.5m｜支持的资源类型

在资源申请场景中，目前已经支持 9 类资源。

数据与存储类包括 Cloud Storage、BigQuery、Cloud SQL 和 Spanner；运行与集成类包括 DataFlow、Pub/Sub 和 Artifact Registry；安全与可观测性类包括 Secret Manager 和 Metrics。

用户不一定会用系统标准名称描述需求。比如用户可能会说“我要一个数据库”或“我要一个 bucket”。Agent 可以识别这些常见表达，再映射到标准资源类型。

但在真正查询模板、构造申请和提交请求时，系统始终使用标准资源名称。这样既降低了用户的表达门槛，也保证后端处理、模板匹配和审计记录的一致性。

后续如果客户有新的资源类型，只需要在资源目录、模板和相应的 Skill 规则中扩展，不需要重建整个 Agent 平台。

## 第 9 页｜2m｜生产上线准备

项目目前已经完成 Agent 基础架构、前后端实现，以及资源申请闭环的 Dev 环境验证。

当前生产上线依赖 GKE Sandbox 在 Prod Cluster 中可用。Sandbox 就绪后，系统可以将会话工作区、文件和产物管理接入生产运行环境。

因此，项目现在不是概念验证阶段。核心功能已经完成并在 Dev 环境验证，当前重点是完成生产环境接入，让这些已验证的能力服务真实客户。

上线后，我们会继续根据客户使用情况扩展资源类型、成本场景和新的业务 Skill。

## 第 10 页｜5m｜Cloud SQL Dev 演示

下面我演示一次 Dev 环境中的 Cloud SQL 资源申请。这个演示会真实提交 Dev 环境请求，不会影响生产环境。

### 演示前一句话

我现在不从表单开始，而是直接用用户的表达发起申请，观察 Agent 如何理解需求、解释资源属性并推动申请。

### 操作 1：用自然语言发起请求

在输入框中输入：

> 我需要为 `[应用名称]` 在 Dev 环境申请一个 Cloud SQL 实例。

讲解：

这里用户只表达了目标，没有把所有资源属性一次性填完。系统首先识别资源类型为 Cloud SQL，并进入相应的 Skill。

### 操作 2：展示属性解释和信息收集

根据页面提示，逐步补充实例名称、区域、数据库版本、规格或其他 Dev 环境必填信息。

讲解：

当某项资源属性不清楚时，用户可以直接追问。Agent 会结合 JSON Schema 和资源模板，用业务语言解释这个属性的含义与用途，再继续收集信息。

如果页面显示基础资料沿用确认，说明系统已识别到该会话或用户的已保存资料。这里可以选择“确认”沿用，或者选择修改，展示会话记忆减少重复填写的价值。

### 操作 3：展示校验与确认

完成信息收集后，展示系统生成的申请摘要。

讲解：

此时 Agent 已经把自然语言表达和补充信息整理成标准化申请内容。但系统仍然不会直接提交，因为资源申请属于有副作用的操作。

请注意这里的确认环节。用户可以检查资源名称、环境、关键资源属性和申请理由；只有用户明确确认后，系统才允许调用外部提交能力。

### 操作 4：提交 Dev 请求

点击确认并提交。

讲解：

现在请求会提交到 Dev 环境。这里请根据实际页面结果描述：如果页面返回申请编号，就说“系统已返回申请编号”；如果页面显示已受理，就说“请求已成功受理”。不要将“申请已提交”说成“云资源已经创建完成”，除非外部系统确实返回了创建成功状态。

### 演示收束

这次演示展示了三个重点：用户从自然语言开始，不需要先理解全部资源属性；Agent 在多轮对话中完成解释、收集和校验；最终提交仍然保留用户确认和受控执行边界。

### 演示异常时的备用话术

如果 Dev 环境网络、MCP 或外部服务暂时不可用，可以切换到申请摘要页或准备好的截图，并说：

> 这里的 Dev 环境依赖暂时不可用。我保留了刚才演示的申请摘要，重点仍然是：Agent 已完成资源识别、属性解释、信息校验，并在用户确认前暂停提交。

## 第 11 页｜2m｜面向客户的价值

最后，我用客户价值收束今天的分享。

第一，Danaan Agent 帮助客户降低云平台运营负担。高频咨询和信息补充被前移到对话过程，云平台团队可以把更多精力放在复杂需求和平台建设上。

第二，它帮助客户提升资源治理一致性。资源模板、校验规则和关键确认机制进入申请过程，资源申请不再依赖每个用户对规则的个人理解。

第三，它让客户的成本决策更有依据。历史费用查询和新用例成本估算可以在同一入口提供支持，让资源使用和成本讨论更早发生。

更长期来看，资源申请只是第一个验证场景。客户可以在同一平台继续接入新的资源类型、成本场景和业务 Skill。

这就是 Danaan Agent 的价值：它把单次资源申请能力，沉淀为客户可以持续扩展的智能云服务入口。谢谢大家，欢迎交流。
