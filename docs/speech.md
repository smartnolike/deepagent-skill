# 云资源自助服务平台
TEK Standard Cup · 8分钟演讲稿

## 第1页：开场介绍
**00:00 — 00:20｜20秒**

各位领导、各位同事，大家好。

今天很高兴有机会和大家分享我和Sunny在 HSBC Platform 团队交付的一个项目——云资源自助服务平台。

这个项目不仅解决了传统云资源申请效率低的问题，也通过引入 AI Agent，实现了从人工服务到智能化自助服务的转变。

接下来，我将从项目背景、技术实践、客户价值，以及对 TEK 的价值四个方面进行介绍。

## 第2页：我的角色与项目背景
**00:20 — 01:20｜1分钟**

首先介绍一下我们的项目背景。

我们的客户是 HSBC，主要服务于 Platform 团队，业务涉及云资源的申请、部署和日常支持。

在项目建设之前，客户主要面临三个问题。

第一，缺少统一的云资源申请入口。之前用户需要通过人工沟通或者自己填写 JSON 文件来提交资源申请，整个流程比较分散。

第二，大量重复性的申请和跟进工作占用了 Support 团队的时间，使他们很难投入到更有价值的技术工作中。

第三，团队缺少统一的资源管理视图，无法直观地了解当前管理了多少 Project，多少UseCase以及整体的资源规模。

因此，我们希望建设一个统一的云资源自助服务平台，让用户能够通过传统表单或者 AI 对话的方式，自主完成资源申请，并查看审批和部署状态。

项目是2024年3月启动，TEK 团队也从最初的一人发展到两人。

在这个项目中，我们两主要以 Technical SME 的角色参与交付，重点负责前后端架构设计，Agent、Skill、MCP 和 Sandbox 的集成。

我们的核心目标，就是把重复性的人工工作转化为标准化的自助服务。

## 第3页：我们具体做了什么
**01:20 — 03:20｜2分钟**

明确了客户的问题之后，接下来介绍我们是如何解决这些问题的。

首先，从 TEK Standard 的角度来看，我们重点关注客户价值、交付范围和团队职责。

在客户价值方面，我们梳理了原有 JSON 提单流程中的资源字段和填写规则，将这些规则转化为 Portal 的自助申请能力。

目前，平台管理着大约130+ Project，300+ UseCase, 每周处理超过200个自助申请工单。

在交付范围方面，我们明确了 Portal、Agent、MCP、Backend 以及 Sandbox 等模块的职责边界，并通过端到端验收清单和发布顺序来支持整体交付。

在团队分工方面，Sunny 主要负责传统提单系统的需求设计、开发和上线，我主要负责 AI Agent 系统的设计、开发和上线。

接下来，我重点介绍一下这个项目的技术亮点。

对于银行这样的金融机构，引入 AI 并不只是让 AI 能够完成任务，更重要的是，如何保证 AI 在安全、合规和可控的范围内完成任务。

因此，我们采用了双入口、统一后端的架构设计。

对于传统用户，他们可以直接通过 Portal 填写表单，由 Backend 处理后续的业务流程。

而对于 AI 用户，他们只需要通过自然语言描述自己的需求。

例如，用户可以告诉 AI：“我需要申请一个 Cloud SQL 数据库。”

Agent 会通过 Skill 理解业务规则，收集并补充申请所需的参数，再通过受控的 MCP 调用 Backend 的业务接口。

涉及实际写入的操作，需要经过相应的用户确认和后端业务流程。

这里最关键的一点是：**AI 并不会绕过原有的权限校验、审批和部署机制。**

我们还引入了基于 GKE 的 Sandbox，将 Skill 所需的命令执行和文件操作放在隔离环境中，进一步控制执行风险。

最终，我们形成了五个核心交付模块，分别负责用户交互、Agent 编排、MCP 工具封装、后端业务处理和隔离执行。

通过这样的设计，我们既保留了传统业务流程的稳定性，也充分利用了 AI 在自然语言交互和任务编排方面的能力。

## 第4页：为客户创造的实际价值
**03:20 — 04:30｜1分10秒**

那么，这个平台上线之后，究竟给客户带来了什么价值？

我们主要从三个维度进行衡量。

第一个是时间成本。

平均每个申请工单的处理时间，从原来的120分钟缩短到了20分钟，整体处理时间减少了约83%。

第二个是人力投入。

Support 团队每周投入在重复工单上的时间，从40个小时降低到了8个小时，减少了80%。

这意味着团队每周可以释放32个小时，将更多精力投入到复杂问题处理和平台能力建设中。

第三个是质量和风险。

通过标准化的申请流程和受控的执行机制，风险率从12%下降到了6%，降幅达到50%。

这里还有两个比较直观的业务场景。

ACE 数据处理框架的部署权限处理，从原来的10天缩短到了1天。

Cloud SQL 数据库的申请，从原来的48小时缩短到了2小时。

这些数据体现出，我们交付的不仅仅是一个新的申请门户，更是对客户原有工作流程的一次优化。

客户获得了更高的服务效率，Support 团队减少了重复性工作，同时整个资源申请过程也变得更加标准化和可控。

## 第5页：对TEK的价值——技术沉淀与分享
**04:30 — 06:00｜1分30秒**

除了为客户创造直接的业务价值，我们也在思考，这个项目能够为 TEK 留下什么。

我认为，这个项目比较有价值的地方，是我们沉淀了一套将 AI Agent 与企业现有业务系统相结合的技术方案。

目前，我们已经形成了自助提单平台的技术文档包，主要包含三个方面。

第一，是传统表单与 AI 对话双入口的架构设计。

这套架构可以帮助其他项目在保留现有业务系统的基础上，逐步引入 AI 能力，而不需要完全重构原有系统。

第二，是 Agent、Skill 和 MCP 的集成方案。

通过 Skill 沉淀业务规则，通过 Agent 进行任务编排，再通过 MCP 将现有业务能力封装为可控的工具。

这种模式不仅适用于云资源申请，也可以应用到其他企业内部的业务流程中。

第三，是基于 GKE 的部署和隔离执行方案，为企业级 AI Agent 的运行提供技术参考。

在这些技术沉淀中，Sunny 主要贡献了提单系统架构、MCP 服务、Skill 开发以及部署验收方面的经验。

我主要贡献了 Agent 架构设计，以及 Skill、MCP 和 Sandbox 的集成经验。

当然，目前这些内容还没有在 TEK 内部开展正式的团队分享和跨团队分享,但是在HSBC已经有了很多次分享。

下一步，我们计划对项目材料进行脱敏，将客户项目中的实践经验整理成可复用的技术案例，再面向相关的云平台和 AI 项目团队进行分享。

我们的目标，是让这些经验不只是停留在当前项目，而是逐步转化为 TEK 可以持续积累和复用的技术资产。

## 第6页：对TEK的价值——复制与业务拓展
**06:00 — 07:40｜1分40秒**

在技术沉淀的基础上，我们进一步思考，这套方案未来可以复制到哪些场景，以及能够为 TEK 带来哪些新的机会。

我认为主要有三个方向。

第一个方向，是 HSBC 内部的其他项目。

目前我们的平台主要服务于云资源申请，但类似的自助服务模式，也可以进一步扩展到权限申请、资源变更，以及其他重复性的云平台支持场景。

第二个方向，是 TEK 的其他客户。

对于已经使用云平台，但仍然依赖人工处理资源申请和审批流程的客户，我们可以将这个项目作为一个参考案例，帮助他们建设类似的自助服务平台。

第三个方向，是其他行业。

只要企业具备内部云平台或者开发者平台的建设需求，就有机会复用我们沉淀的分层架构、AI 辅助提单和受控执行模式。

除此之外，我们还看到一个更值得关注的潜在机会，就是 Agent Platform 的建设。

目前，我们已经在项目中实践了 Agent 编排、Skill 集成、MCP 工具调用和 Sandbox 隔离执行等核心能力。

未来，我们可以进一步将这些能力平台化，提供统一的 Agent 开发、发布、受控工具调用和运行管理能力，让更多业务团队能够在统一的平台上建设自己的 AI Agent。

这样，我们就有机会从交付一个具体的 AI 应用，逐步拓展到交付企业级 AI 平台能力。

当然，目前这些复制和拓展方向还处于构想阶段。

下一步，我们计划整理完整的项目案例包，与 AM 和 DL 一起评估 HSBC 其他团队的适用场景，并通过内部技术分享识别更多潜在的复用机会。

我们希望通过这个项目，不仅解决当前客户的问题，也为 TEK 在云平台和企业级 AI 领域的后续业务拓展提供技术基础。
